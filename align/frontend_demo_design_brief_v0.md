# 前端交互演示设计 brief v0

## 1. Confirmed Decisions

- 演示定位：考生端核心推荐交互 demo，展示真实系统现场跑一次的过程。
- 录制策略：答辩或展示前提前跑通并录制视频，因此优先追求真实链路可信度，而不是纯静态样机稳定性。
- 运行环境：使用 `source activate gaokao_pg` 启动环境；如 Windows PowerShell 不支持该命令，则使用 Conda 激活脚本或 `C:\ProgramData\Anaconda3\envs\gaokao_pg\python.exe` 做等价验证。
- 后台范围：管理员后台可以不做；登录、权限、账号、部署、数据管理后台均不进入本轮。
- 数据口径：候选学校、专业、分数、位次、学费等事实必须来自 PostgreSQL / 标准化证据层；LLM 只做语义归一、探针规划和表达组织。
- 论文口径：演示主张要符合最终论文与 confirmed fact ledger，不把系统说成生产级替代升学顾问。
- 交互口径：不能只给一个抽象取舍问题；页面必须先亮出当前范围内的前几个候选，再亮出一个放宽后找到的引导候选，并说明它相对当前候选的优势和放宽维度。

## 1.1 Recommendation Interaction Alignment

- 位次估计：分数转位次使用 `score_rank_segments.rank_max` 作为单点估计值；浙江 2025 年 600 分在当前库中展示为 `r=52529`，不再给区间。
- 地域字段：`province` 保留为考生省份，用于分数位次换算；若用户说“江浙沪”等多省目标，另用 `target_provinces` 过滤目标院校所在地。
- 当前候选召回：先只用非分数类硬性条件初筛，包括省份/城市、选科、预算、专业词和本科质量过滤；不再用 `min_score <= score` 直接截断当前候选。
- 冲稳保分桶：设考生估计位次为 `r`，候选最低录取位次为 `c`，按 `c/r` 分桶：冲 `0.85-0.98`，稳 `0.98-1.15`，保 `1.15-1.40`。
- 桶内排序：每个桶内按当前偏好权重下的 `_implicit_utility` 从高到低排序，每桶取 Top 3；用户反馈更新权重后，下一轮排序必须随权重变化。
- 展示方式：首轮即展示当前范围内的冲/稳/保候选矩阵，再展示一个放宽后找到的跃迁候选，用于说明“放宽了什么”和“换来了什么”。
- 事实边界：学校、专业、分数、位次、学费、层级、位置等字段来自数据库；自然语言解释可以由 LLM 组织，但不能编造候选事实。

## 2. Audience

- 第一受众：答辩老师或评审，关心系统是否真实落地、交互机制是否和论文方法一致。
- 第二受众：演示观看者，关心考生如何从模糊需求走到可解释推荐。
- 第三受众：后续维护者，关心前端是否能清楚暴露后端状态、候选证据和偏好更新。

## 3. Primary Workflow

演示一条完整用户路径：

1. 用户输入首轮需求，例如分数、省份、选科、专业倾向、地域和预算。
2. 系统抽取显式约束，调用真实后端 `/api/v1/chat`。
3. 页面展示当前硬约束范围内前几个 baseline 候选、硬约束锁定项和待澄清偏好轴。
4. 页面突出一个 Pareto 放宽引导候选，说明放宽维度，例如地域、专业邻近度、预算、风险、学校/学科实力，并解释它相对当前候选的优势。
5. 系统生成 Pareto A/B 取舍问题，例如名校层次、专业匹配、预算、地域之间的替代关系。
6. 用户点击或输入反馈，系统更新偏好状态。
7. 页面展示 BT 后验权重变化、候选排序变化和最终推荐报告。
8. 演示结束时展示运行轨迹摘要：`semantic_normalizer -> gatekeeper -> radar -> negotiator -> preference_tracker`。

## 4. Non-goals

- 不做登录注册。
- 不做管理员数据维护后台。
- 不做招生数据编辑、批量导入或人工审核工作台。
- 不把现有竞品页面截图作为主要演示素材。
- 不使用 AI 生成学校、专业、分数、位次、学费等事实。
- 不承诺真实用户有效性、跨省跨年份泛化或生产级稳定性。

## 5. Information Hierarchy

- 一级信息：当前用户需求、系统下一问、用户反馈入口。
- 二级信息：当前范围内前几个候选、一个放宽引导候选、放宽维度和优势解释。
- 三级信息：其他候选卡片、证据字段、冲稳保/排序结果。
- 四级信息：约束锁定、偏好权重、UCB 选轴、BT 后验更新。
- 五级信息：运行轨迹、原始 API 响应、调试日志摘要。

界面应让评审第一眼看到“这不是静态推荐列表，而是多轮偏好澄清系统”。

## 6. Interaction States

- 初始态：预填一条可演示样例，但允许现场编辑。
- 约束缺失态：如果分数或选科缺失，系统提示补充，而不是直接推荐。
- 候选生成态：展示真实 API loading 状态和本轮调用耗时。
- 澄清态：展示 A/B 取舍卡片，用户可点击“偏向 A”“偏向 B”“仍不确定”，也可输入自由文本。
- 更新态：展示偏好权重和候选排序变化。
- 终局态：展示可解释推荐报告和证据摘要。
- 错误态：明确显示数据库、模型或 API 错误；录制前必须修复，演示时不默认降级为伪数据。

## 7. Visual Constraints

- 工具型决策台风格，避免营销 landing page。
- 信息密度要高，但每屏不要堆满公式；公式和算法名只作为审计/解释辅助。
- 卡片圆角不超过 8px，避免装饰性大渐变和无关插画。
- 页面优先适配 1440x900 录屏，也要在常见笔记本宽度下不重叠。
- 推荐候选卡片必须突出事实字段：学校、专业、省市、最低分/位次、学费、风险或推荐理由。
- 放宽引导候选必须明确显示“放宽了什么”和“换来了什么”，例如更高学校层次、985/211/双一流标签、更靠前排名、更高学科质量或更强就业画像。
- 权重变化、UCB 选轴和 BT 更新可以用小型条形图/雷达图/状态摘要表示，但不伪造实验图表。

## 8. RALPLAN-DR

### Principles

- 真实链路优先：前端要调用现有 FastAPI/LangGraph 后端。
- 事实边界优先：事实候选只来自数据库和探针结果。
- 演示可控：提前录制，所以允许牺牲一点容错 UI，换取真实运行证据。
- 改动收敛：优先改 `app/web` 与必要 API 包装，不重构核心推荐算法。

### Decision Drivers

- 能否完整展示论文的多轮偏好澄清闭环。
- 能否在 `gaokao_pg` 环境下稳定复现。
- 能否避免把 demo 做成和论文不一致的静态推荐页面。

### Viable Options

| Option | Description | Pros | Cons |
| --- | --- | --- | --- |
| A. 真实系统优先 | 前端直接调用 `/api/v1/chat`，围绕真实响应渲染交互 | 最贴近论文和系统实现；录屏可信 | 依赖数据库、模型、环境和现场服务 |
| B. fixture 优先 | 固定样例数据驱动完整流程 | 最稳定，适合现场点击 | 容易被看成静态样机 |
| C. 混合模式 | 默认真实 API，保留明确标注的 demo fixture 兜底 | 兼顾稳定和可信 | 需要额外 UI 标识，避免混淆 |

### Decision

采用 A 作为主线：真实系统优先。因为用户会提前录制视频，主要风险可以通过预跑、录屏和服务检查吸收。

可保留 C 的工程接口，但兜底数据必须显式标注为 `demo fixture`，不能在录制成片中冒充真实运行结果。

## 9. ADR

- 决策：新增或重做一个考生端 demo 页面，挂载在 FastAPI，例如 `/demo`。
- 依据：当前项目已有 `main.py`、`app/api/chat_api.py`、`app/web/index.html`、`app/web/ui_showcase.html`，最小改动即可形成真实交互入口。
- 取舍：不引入 React/Vite，除非后续明确要长期产品化；本轮用原生 HTML/CSS/JS 更快、更少依赖、更容易录制。
- 后端：优先复用 `/api/v1/chat`；如现有响应字段不足，可增补一个只读 demo summary 字段，但不改变核心算法。
- 验证：启动服务后用浏览器录屏路径实测，而不是只跑静态文件检查。

## 10. Key Changes Plan

1. 新增 `app/web/demo.html` 或重写 `app/web/index.html` 为真实交互页。
2. 在 `main.py` 添加 `/demo` 路由，保留 `/ui-showcase` 作为静态参考。
3. 前端实现：
   - 初始画像输入区。
   - 多轮对话区。
   - A/B 取舍按钮和自由反馈输入。
   - 候选证据卡片。
   - 约束锁定与偏好权重面板。
   - 运行轨迹摘要。
4. 必要时扩展 API 响应：
   - `ucb_target_dimension`
   - `implicit_weights`
   - `weight_variance`
   - `latest_pareto_diff`
   - `opportunity_rankings`
5. 增加启动/录制检查说明，例如 `align/frontend_demo_runbook_v0.md`。

## 11. Test Plan

- 环境验证：`source activate gaokao_pg` 后能导入 `main.app`。
- 服务验证：启动 `uvicorn main:app --host 127.0.0.1 --port 8000`，访问 `/health` 返回 ok。
- API 验证：用一条浙江考生样例 POST `/api/v1/chat`，确认返回候选、约束或澄清问题。
- 浏览器验证：打开 `/demo`，完成至少两轮交互，截图或录屏确认页面无重叠、无乱码、无空白核心区。
- 内容验证：候选事实字段来自 API 响应；若出现 fixture，页面必须显式显示 fixture 标识。
- 演示验证：录制前固定一条推荐脚本，确认每一步可复现。

## 12. Open Checks Before Implementation

- 当前 PostgreSQL 服务是否已启动并监听 `127.0.0.1:55432`。
- 当前 `.env` 中模型与数据库配置是否可用于录制；不读取或输出密钥。
- `/api/v1/chat` 在真实环境下是否能跨两轮保持 thread state。
- 现有 `app/web/ui_showcase.html` 是否要保留为视觉参考，还是在新 `/demo` 页面中吸收其布局元素。

## 13. Acceptance Criteria

- 录制视频里可以看到真实 API 调用完成，而不是静态页面切换。
- 用户至少完成一次 A/B 取舍反馈。
- 页面显示偏好状态或候选排序随反馈变化。
- 页面明确展示事实候选来源边界。
- 演示过程中不需要登录，不需要管理员后台。
- 1440x900 录屏下主要文字不遮挡、不溢出、不乱码。
