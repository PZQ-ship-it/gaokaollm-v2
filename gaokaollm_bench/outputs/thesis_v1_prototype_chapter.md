## 3.1 原型系统定位

高考志愿咨询系统首先需要解决的是工程可用性问题。用户提出的问题往往同时包含分数、选科、省份、学校、专业、地域偏好和风险偏好等信息，且多轮对话中会不断补充或修正条件。第一版 `gaokaollmmodel` 的目标，是构建一个能够在真实招生数据约束下完成问答、检索和推荐的 Agentic RAG 原型系统。

与单轮 RAG 问答相比，v1 更强调“智能体式”的系统编排。系统并不是把用户问题直接拼接到提示词中生成答案，而是通过 LangGraph/状态机工作流，将安全检查、状态追踪、问题改写、意图识别、检索路由、结构化查询、混合检索和最终生成拆成多个节点。每个节点承担相对明确的职责，节点之间通过状态对象传递用户画像、对话历史、检索结果和生成上下文。

因此，v1 在论文中的合理定位不是最终主贡献，而是“工程原型与问题发现”。它证明了高考志愿咨询可以被构建为一个端到端 Agentic RAG 系统，也暴露出仅靠工程问答系统难以证明偏好妥协效果的问题。后续 v2 正是在这一问题上继续收敛：从“系统能回答志愿问题”升级为“系统能被严格评测，并能用真实证据触发用户偏好妥协”。

## 3.2 系统总体架构

v1 系统可概括为“图状态机编排 + 用户画像缓存 + 混合检索 + 约束一致性校验 + 流式交互”的 Agentic RAG 架构。整体流程如下：

```text
用户输入
  -> 安全检查
  -> 状态追踪与用户画像更新
  -> 问题改写与一致性校验
  -> 意图识别与任务路由
  -> SQL 检索 / 向量检索 / 混合检索 / 分层推荐
  -> 生成回答
  -> SSE 流式返回
```

建议论文绘图：图 3-1 “第一版 Agentic RAG 原型系统架构图”。图中可展示用户输入、LangGraph 工作流、Redis 用户画像、MySQL/PostgreSQL/向量数据库、BGE-M3、BCEmbedding reranker、生成模型和前端 SSE 响应之间的数据流。

| 模块 | 主要职责 | 论文作用 |
|---|---|---|
| LangGraph/状态机工作流 | 编排安全检查、状态追踪、改写、意图识别、检索和生成节点 | 说明 v1 已具备 Agentic RAG 工程闭环 |
| 意图识别与任务路由 | 区分分数、选科、学校、专业、地域和复合查询 | 解决多类型高考咨询问题的入口分流 |
| Redis 用户画像 | 缓存省份、分数、选科、偏好等多轮状态 | 缓解上下文漂移和用户信息丢失 |
| 混合检索 | 结合结构化过滤、向量召回和重排序 | 支撑事实约束下的志愿问答 |
| `1:3:9` 冲稳保推荐 | 生成可冲击、较稳妥、可保底的梯度方案 | 作为 v2 `risk_band_relax` 的工程来源 |
| 神经-符号一致性校验 | 防止模型改写或生成时污染真实分数和用户画像 | 为后续事实审计提供早期经验 |
| SSE 流式响应 | Token 级输出，改善用户感知延迟 | 体现原型系统的工程完整性 |

## 3.3 LangGraph/状态机工作流

v1 采用 LangGraph 的 `StateGraph` 构建工作流。代码中可见的核心节点包括 `security_check_node`、`state_trace_node`、`rewrite_node`、`check_rewrite_consistency_node`、`intention_recognition_node`、`designed_retriever_node`、`combined_retriever_node`、`university_score_retriever_node`、`subject_requirement_retriever_node` 和 `agent_node` 等。

这种状态机式设计的价值在于把高风险咨询任务拆解为可控步骤。安全检查节点负责拦截无关或不支持请求；状态追踪节点负责抽取并更新用户省份、分数、选科和偏好；问题改写节点负责处理省略、指代和上下文补全；一致性校验节点检查改写结果是否篡改用户真实信息；意图识别节点决定后续调用哪一类检索或推荐链路；最终生成节点把检索结果组织成自然语言回答。

论文中可将该工作流写成 v1 的第一个关键经验：高考志愿咨询不适合仅用单 prompt 完成，必须通过显式状态和节点职责降低复杂任务中的信息混淆风险。

## 3.4 意图识别与状态追踪

v1 中的意图识别模块面向高考咨询的典型问题类别，包括录取分数查询、选科要求查询、学校信息查询、专业信息查询、地域相关查询和分数段推荐等。中期报告中已经指出，早期系统存在任务类别区分混乱的问题，因此 v1 对意图识别节点进行了重构，支持“分数 + 选科”等复合查询，并引入输入守卫机制处理非法分数、不支持功能和无上下文意图。

状态追踪模块与 Redis 用户画像结合使用。系统会把用户在多轮对话中给出的省份、分数、选科、地域偏好、专业偏好等信息写入画像缓存，并在后续轮次中复用。该设计解决了多轮对话中常见的“用户已经说过但模型忘记了”的问题，也降低了每轮都要求用户重复条件的交互成本。

但这一设计也暴露了 v1 的一个关键风险：用户画像一旦被模型改写、检索结果或上下文记忆污染，后续所有推荐都会基于错误状态展开。为此，v1 引入了神经-符号一致性校验，将模型输出与规则校验结合起来，重点保护真实分数、选科、省份等关键约束。

## 3.5 混合检索与二阶重排

高考志愿问答同时依赖结构化数据和非结构化文本。分数、位次、批次线、选科要求和学校属性适合通过 SQL 或结构化过滤处理；招生章程、专业介绍和解释性材料则更适合向量检索。v1 因此采用混合检索策略，将关系型过滤与稠密向量召回结合起来。

在向量侧，v1 接入 BGE-M3 embedding，并使用 BCEmbedding reranker 进行二阶重排。中期报告将该链路概括为“30 选 10”的 Top-K 二阶检索：先通过向量召回获得候选，再通过重排模型筛选更相关的结果。该设计的目的不是单纯提高文本相似度，而是让高考志愿咨询中的专业、学校和政策解释具有更稳定的召回来源。

在结构化侧，系统围绕招生分数表和省份、学校、专业等实体进行过滤。例如，用户询问某专业在某省的录取分数时，系统需要同时匹配年份、录取省份、学校、专业和最低分等字段。相比开放域问答，高考志愿场景对字段一致性要求更高，检索错误会直接导致推荐不可用。

## 3.6 `1:3:9` 冲稳保推荐策略

v1 的一个重要工程能力是 `1:3:9` 冲稳保推荐策略。系统将候选志愿组织为“可冲击、较稳妥、可保底”三类，并要求生成时分别给出推荐理由。该策略贴近真实志愿填报中的梯度组合思想：用户不应只看到单一安全选项，也不应只看到风险过高的冲刺选项，而是需要在不同风险层级之间形成组合。

v1 中的冲稳保主要作为推荐生成策略存在，其目标是让系统输出更接近真实填报习惯。它已经体现出“风险组合”思想，但还没有被放入多轮偏好妥协 benchmark 中检验。也就是说，v1 能生成梯度推荐，并不等于已经证明用户会在看到证据后从“只求稳”转向接受冲稳保组合。

这一点正是 v2 `risk_band_relax` 的来源。v2 保留 v1 的工程直觉，但把它升级为可评测闭环：在用户显性表达“只求稳、不想冲”的情况下，Agent 只放宽风险偏好，不放宽省份、专业、选科和预算等硬约束，并用 PostgreSQL 中的最低分、最低位次、`score_margin`、`rank_gap` 和 `chong/wen/bao` 风险层级证据触发用户隐藏妥协。`risk_band_v1` 中 `app_pareto 1.000 / 3.000 / 0.000 / 5.00` vs `hard_constraint 0.000 / 0.000 / 0.000 / 15.00` 的结果属于 v2 主实验，不混入 v1 成果。

## 3.7 神经-符号一致性校验与防幻觉经验

高考志愿咨询中的幻觉风险不只表现为编造学校或专业，也表现为对用户真实分数、选科、省份和检索结果的误读。中期报告中提到，v1 曾遇到多轮对话中的记忆污染问题，例如模型可能把参考录取线误认为用户真实分数。为此，系统设计了神经-符号一致性校验拦截器。

“神经”部分来自 LLM 的语义理解、问题改写和自然语言生成能力；“符号”部分来自规则、正则表达式、字段校验和数据库结果约束。系统在模型输入和输出之间加入校验逻辑，确保关键字段不会被模型擅自改写。例如，用户真实分数必须来自用户话语或 Redis 画像，而不能来自上下文中的学校最低分；选科字段必须符合标准科目组合；省份字段需要区分“用户所在/录取省份”和“学校所在地”。

这部分经验对 v2 有直接启发。v2 的论文主线要求 Agent 的谈判证据必须来自用户显式话语和 PostgreSQL 查询结果，而不是模型自由生成。v1 的一致性校验提供了早期工程经验，v2 则进一步把这一要求纳入 benchmark 的 deterministic factual judge 和 transcript 审计中，形成可量化的 `mean_hallucination_rate` 指标。

## 3.8 流式响应与工程完整性

v1 还实现了面向真实交互的 SSE 流式响应。系统通过后端接口将 Agent 的生成过程以 token 或 chunk 的形式返回前端，改善用户感知延迟。中期报告中还提到，系统在工程侧尝试了 Flash Attention、Chain of Draft 和全链路计时监控等推理提速手段。

这些内容体现了 v1 的工程完整性，但在最终论文中不宜占据过多篇幅。原因是本文最终主贡献不在推理系统性能优化，而在“数据 + Agent + Benchmark”三贡献闭环。建议正文中保留流式响应作为原型系统完整性的说明，将细粒度性能优化放入附录或实现细节部分。

## 3.9 原型系统问题诊断

v1 证明了高考志愿咨询可以被构建为 Agentic RAG 系统，但它也暴露了最终论文需要进一步解决的问题。

第一，v1 的评测更多面向工程功能正确性，例如意图路由是否准确、检索是否能返回结果、生成是否符合格式、接口是否能流式响应。这些指标不足以回答“Agent 是否真正改善了用户决策”。

第二，v1 能给出 `1:3:9` 冲稳保推荐，但缺少一个能模拟用户显性红线和隐性妥协的 benchmark。因此，系统生成了梯度方案，并不意味着用户真的会接受风险偏好放宽，也不意味着该放宽带来了可度量的 Pareto gain。

第三，v1 的防幻觉机制主要服务于单系统内部的稳定运行，而不是服务于论文级审计。毕业论文需要的不只是“系统尽量不幻觉”，还需要 transcript、report、summary、逐例 evidence 和 SHA256 审计报告来证明实验结论可追溯。

第四，v1 仍然偏向“回答用户提出的问题”。但高考志愿咨询中的关键价值往往不在顺从用户初始红线，而在识别哪些红线是信息不足造成的初始锁定，并在真实数据约束下展示放宽后的收益。这需要把系统从问答型 RAG 推进到证据驱动 Pareto 谈判 Agent。

## 3.10 从 v1 到 v2 的过渡

v1 到 v2 不是推翻关系，而是研究问题的收敛和方法升级。v1 解决的是“能否做出一个可用的高考志愿 Agentic RAG 系统”；v2 解决的是“如何证明一个 Agent 在真实招生数据约束下，能够通过多轮证据谈判触发用户偏好妥协”。

| 维度 | v1：`gaokaollmmodel` | v2：数据 + Agent + Benchmark 闭环 |
|---|---|---|
| 论文定位 | v1 是工程原型与问题发现 | v2 是最终主贡献 |
| 核心问题 | 如何让系统能查、能答、能推荐 | 如何让偏好妥协可生成、可运行、可评价 |
| 系统形态 | Agentic RAG 原型 | 数据层 + 轻量 MAS/多角色 Agent + Benchmark |
| 数据贡献 | 数据作为问答和推荐的运行依赖 | PostgreSQL 招生快照、分数/位次、学费、专业树、`school_major_quality_profiles`、`major_employment_outcome_profiles` |
| Agent 架构 | LangGraph/状态机、Redis 画像、混合检索、BGE-M3、BCEmbedding、`1:3:9`、SSE | `gatekeeper -> radar -> negotiator` 轻量 MAS/多角色 Agent 工作流 |
| 主要能力 | 查分、问答、混合检索、梯度推荐和一致性校验 | `major_geo_relax`、`risk_band_relax`、`tuition_value_relax`、`major_quality_relax`、`employment_outcome_relax` |
| 风险推荐 | 工程化冲稳保输出 | 可评测的 `chong/wen/bao` 风险偏好放宽 |
| 证据链 | 系统日志和工程测试为主 | transcripts、reports、summary、evidence、audit |
| 实验归属 | 不承载 `app_pareto` 主实验指标 | 承载 `major_geo_v1 + risk_band_v1` 主实验，以及 `school_strength_v1 + tuition_value_v1 + major_quality_v1 + employment_outcome_v1` 扩展实验 |

后续章节可以按如下逻辑承接：

```text
第 3 章：v1 跑通 Agentic RAG 原型，并诊断出偏好妥协评测不足
第 4 章：v2 构建 PostgreSQL 数据层、专业树、质量/就业标准化层和冰山画像 Benchmark
第 5 章：v2 设计 gatekeeper -> radar -> negotiator 轻量 MAS/多角色 Pareto 谈判 Agent
第 6 章：v2 用主实验和扩展实验验证 Agent 相对 baseline 的提升与数据证据维度的可扩展性
```

## 3.11 与 v2 实验结果的边界

论文写作中必须明确：六组 `app_pareto` 与 `hard_constraint` 对照实验均属于 v2 的数据 + Agent + Benchmark 闭环，不是 v1 原型系统的实验结果。其中 `major_geo_v1` 与 `risk_band_v1` 是 v2 的 Agent-vs-Baseline 主实验，四组扩展实验用于支撑数据贡献和框架可扩展性。

当前 v2 实验结果为：

| 实验 | `app_pareto` | `hard_constraint` | 归属 |
|---|---|---|---|
| `major_geo_v1` | `0.900 / 0.900 / 0.000 / 5.20` | `0.000 / 0.000 / 0.000 / 7.00` | v2 主实验 |
| `risk_band_v1` | `1.000 / 3.000 / 0.000 / 5.00` | `0.000 / 0.000 / 0.000 / 15.00` | v2 主实验 |
| `school_strength_v1` | `1.000 / 15.000 / 0.000 / 5.00` | `0.000 / 0.000 / 0.000 / 11.00` | v2 扩展实验 |
| `tuition_value_v1` | `1.000 / 1.000 / 0.000 / 5.00` | `0.000 / 0.000 / 0.000 / 11.00` | v2 扩展实验 |
| `major_quality_v1` | `1.000 / 16.000 / 0.000 / 5.00` | `0.000 / 0.000 / 0.050 / 11.00` | v2 扩展实验 |
| `employment_outcome_v1` | `1.000 / 49.000 / 0.000 / 3.00` | `0.000 / 0.000 / 0.000 / 11.00` | v2 扩展实验 |

四个指标依次为 `elicitation_success_rate / mean_pareto_gain / mean_hallucination_rate / avg_turns`。其中 `major_geo_v1 + risk_band_v1` 用于证明核心偏好妥协能力，`school_strength_v1 + tuition_value_v1 + major_quality_v1 + employment_outcome_v1` 用于证明同一框架可以接入学科实力、学费、专业质量和就业结果等数据证据维度。这些结果用于证明 v2 的证据驱动 Pareto 谈判能力和数据层可扩展性，不应写成 v1 `gaokaollmmodel` 的直接性能结果。

同时，`major_geo_v1` 并非 100% 成功。失败样本为 `real-db-set-浙江-569-009`。论文中应保留这一失败分析，用来说明当前 Agent 闭环已经可审计，但仍存在放宽阶段选择和候选命中方面的改进空间。

## 3.12 本章小结

本章介绍了第一版 `gaokaollmmodel` Agentic RAG 原型系统。v1 通过 LangGraph/状态机工作流、意图识别、Redis 用户画像、混合检索、BGE-M3 embedding、BCEmbedding 重排、`1:3:9` 冲稳保推荐、神经-符号一致性校验和 SSE 流式响应，完成了面向高考志愿咨询的工程闭环。

但 v1 的主要价值是工程原型与问题发现，而不是最终主贡献。它证明了系统能回答和推荐，也揭示了传统 RAG 原型难以严格评测隐性妥协、动态放宽、Pareto 增益、逐例证据和可复现审计的问题。基于这一诊断，后续 v2 将研究重点转向“数据 + Agent + Benchmark”三贡献闭环：数据层负责提供 PostgreSQL 招生事实、专业树、专业质量和就业结果等可核验证据；Agent 层通过 `gatekeeper -> radar -> negotiator` 轻量 MAS/多角色工作流进行证据驱动 Pareto 谈判；Benchmark 层负责构建冰山画像、多轮沙盒和事实/过程联合评价。主实验 `major_geo_v1 + risk_band_v1` 证明核心偏好妥协能力，四组扩展实验则证明数据证据维度可以持续接入同一闭环。
